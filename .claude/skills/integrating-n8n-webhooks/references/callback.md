# Колбек: n8n → Next.js

Читати перед тим, як писати `app/api/n8n/[event]/route.ts`.

## Ендпоінт

`POST /api/n8n/<event>` — Route Handler `app/api/n8n/[event]/route.ts`. Route Handler — публічний
HTTP-ендпоінт, тож довіряємо лише підпису. `<event>` у шляху — та сама подія, що в запиті до n8n
(`quote-request`); у тілі колбека — `<event>.completed` або `<event>.failed`.

| Заголовок | Значення |
|---|---|
| `content-type` | `application/json` |
| `x-n8n-timestamp` | Unix-час у секундах, коли n8n підписав запит |
| `x-n8n-signature` | `sha256=<hex HMAC-SHA256(N8N_CALLBACK_SECRET, "${timestamp}.${rawBody}")>` |
| `idempotency-key` | `<data.jobId>:<event з тіла>` — ті самі значення, що в підписаному тілі |
| `x-correlation-id` | скопійований із запиту, що запустив воркфлоу |

Тіло:

```json
{
  "version": 1,
  "event": "quote-request.completed",
  "data": {
    "jobId": "5f0c…",
    "status": "completed",
    "correlationId": "9b1e…",
    "requestIdempotencyKey": "c3d4…",
    "result": { "documentUrl": "https://files.example.test/n8n/5f0c….pdf" },
    "completedAt": "2026-09-21T12:00:00.000Z"
  }
}
```

`data.status` — `completed` або `failed` (тоді замість `result` — `error: { code }`).
`data.requestIdempotencyKey` — ключ нашого запиту до n8n: за ним знаходимо запис, який чекає результату.

## Порядок обробки — саме такий

1. Подія зі шляху невідома (шукаємо лише власні ключі обробників — `Object.hasOwn`, щоб `/constructor` не
   знайшов `Object.prototype`) → **404**; тип тіла (частина `content-type` до `;`) не рівно `application/json`
   → **415** (`application/json; charset=utf-8` — так, `application/jsonp` — ні). Обидві перевірки — до читання тіла.
2. Заявлений `content-length` більший за 64 КБ → **413** ще до читання. Потім тіло — як **сирий текст**, але з
   жорстким лімітом під час читання: потоком (`request.body.getReader()`), і щойно прочитано понад 64 КБ —
   припинити читання й відповісти **413** (шаблон `lib/n8n/body.ts`). Лише `content-length` не досить: у
   chunked-тіла його немає, а заявлене значення може бути неправдою. Route Handler розмір тіла не обмежує
   (`experimental.proxyClientMaxBodySize` діє лише на запити, що йдуть через proxy), тож інакше будь-хто без
   секрету змусив би сервер тримати в пам'яті мегабайти. Тіло читається лише раз. Ні `request.json()`, ні
   `JSON.parse` до перевірки підпису: повторна серіалізація змінює байти, і підпис не зійдеться.
3. Колбек несе посилання, а не файли, тож 64 КБ досить із запасом.
4. `x-n8n-timestamp` відрізняється від поточного часу більш ніж на **300 с** у будь-який бік → **401**. Вікно —
   наше рішення проти повторного відтворення (replay).
5. Порахувати HMAC від `` `${timestamp}.${raw}` `` і порівняти з підписом: спершу довжини, потім
   `crypto.timingSafeEqual` (на різних довжинах він кидає помилку). Не `===`. Не збігається → **401** без
   подробиць у тілі. Секрет порожній, заглушка `change-me-…` чи коротший за 32 символи → **401** на все:
   заглушка публічна (`.env.example`), і забутий на хостингу секрет дав би підписувати колбеки будь-кому.
6. «Застовпити» `idempotency-key` — унікальний запис у сховищі зі станом: `processing` (обробляється зараз) або
   `done` (збережено). Вже `done` → **200** `{"duplicate": true}`: n8n не повторюватиме, а дані не зміняться
   вдруге. Ще `processing` (та сама доставка паралельно) → **409**: результат ще не збережено, тож «дубліката»
   казати не можна — якщо перша обробка впаде, n8n мусить повторити.
7. Тепер `JSON.parse(raw)` і перевірка форми → **400** (ключ звільнити), якщо:
   - подія в тілі — не `` `${подія зі шляху}.${data.status}` `` (`.completed` зі статусом `failed` — теж 400);
   - `completed` без `result.documentUrl` з протоколом `http(s):` (посилання стане `<a href>`, тож
     `javascript:` — ні), `failed` без `error.code`;
   - `idempotency-key` не дорівнює `` `${data.jobId}:${event}` `` з тіла.
8. Зберегти мінімальний стан (напр. `status = ready`, посилання на документ) **до** відповіді — лише дозволеним
   переходом (compare-and-set): `failed` — з `queued`, `completed` — з `queued` або `failed`. Пізній `failed`
   не стирає готовий результат; колбек, що стану не змінив, — теж 202 (запис є, повторювати нема чого). Якщо після
   кроку 6 обробка впала (4xx/5xx на кроках 7–8) — **звільнити** `idempotency-key`, інакше повтор n8n
   (Retry On Fail) отримає `{"duplicate": true}`, і результат загубиться. Вдалося — позначити ключ `done`.
9. Відповісти **202** `{"ok": true}`.
10. Повільне (листи, сповіщення, інтеграції) — в `after()`.

## Чому так

- **Запис до відповіді:** отримавши 2xx, n8n колбек не повторить. Якби критичний запис жив лише в `after()`
  і впав, результат загубився б назавжди.
- **Ключ звіряємо з тілом:** заголовок `idempotency-key` підписом не захищений — HMAC рахуємо лише від
  `${timestamp}.${raw}`. Хто перехопив підписаний колбек, міг би в межах 300 с надіслати ті самі байти з новим
  ключем, і застосунок обробив би їх удруге. Коли ключ мусить дорівнювати полям підписаного тіла, повтор із
  тим самим ключем — дублікат, з іншим — 400.
- **Сховище ключів** — база чи KV з унікальним обмеженням. Пам'ять процесу годиться лише для демо: на
  serverless-хостингах обробники не ділять стан між запитами.

## Ідемпотентність — з обох боків

- Next.js → n8n: той самий `idempotency-key` у кожній спробі; в n8n одразу за Webhook стоїть Remove
  Duplicates з цим ключем.
- n8n → Next.js: HTTP Request з Retry On Fail повторює колбек; Next.js відсікає повтори за `idempotency-key`
  і приймає лише ключ, що збігається з підписаним тілом.
- Дублікати неминучі (і наші повтори, і Retry On Fail), тож ідемпотентність — обов'язкова, а не бонус.
